# Sentry and Varlock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Report crashes and unexpected microphone failures from OK Tuner to Sentry with readable stack traces, with the source-map upload token supplied from 1Password through Varlock.

**Architecture:** A microphone failure becomes a tagged union, so `update` can tell a fault from a refusal and return a `ReportProblem` Command for the fault. One module, `src/sentry.ts`, owns the Sentry SDK; Foldkit's `crash.report` hook and the Command both call into it. Varlock's Vite plugin resolves `SENTRY_AUTH_TOKEN` from 1Password at build time for Sentry's Vite plugin, which uploads source maps on Vercel builds only.

**Tech Stack:** Foldkit 0.170.0, Effect 4.1.0, `@sentry/browser` and `@sentry/vite-plugin` 11.14.0, `varlock` 1.25.0, `@varlock/vite-integration` 1.5.6, `@varlock/1password-plugin` 2.0.7, Vite 8, Vitest 5 (happy-dom), Bun 1.4.5.

**Spec:** `docs/superpowers/specs/2026-11-24-sentry-design.md`

## Global Constraints

- Commit messages and the pull request carry no attribution lines.
- Dependencies are pinned exactly (no `^`), at the versions under Tech Stack. Those are the newest releases at least seven days old on 2026-11-24.
- Only `src/sentry.ts` and its test import `@sentry/browser`.
- Nothing under `src` imports `varlock/env`.
- Never open, print or `cat` `.env.local`. Never run `varlock load --format …`, `varlock printenv` or `varlock reveal`. The only allowed looks are `bunx varlock load --agent` and a count or length computed inside `bunx varlock run -- <script>`.
- Nothing is sent to Sentry on a visit where nothing went wrong. No user identifiers, cookies, replay, tracing or IP inference.
- Refused microphone permission, an unsupported browser and blocked storage are never reported.
- The three sentences shown to the person stay word for word: `REFUSED`, `UNSUPPORTED`, `UNEXPLAINED` in `src/microphone.ts`; an unexpected error with a non-empty message still shows that message.
- Foldkit conventions (`FOLDKIT.md`): side effects only in Commands; a Command's result Message is named from the Command; no `NoOp`.
- The dev server (`ok-tuner-dev`, `localhost:5273`) serves the working tree. Do not start a second one. After any change to `vite.config.ts` or `.env.schema`, confirm it still serves the app.
- Every task ends green on all four: `bun run test`, `bun run typecheck`, `bun run lint`, `bun run format` (then commit whatever format changed).
- `SKIP_VARLOCK` is never set on Vercel.

## Review Focus

Each line has a test in the task named.

1. **Blocked site storage at start-up.** With a `localStorage` getter that throws, initialising Sentry must not throw and the app must still start. (Task 2)
2. **Sentry unreachable** (ad blocker, offline). With a transport whose `send` rejects, `ReportProblem` still resolves to `CompletedReportProblem` and nothing is thrown. (Task 3)
3. **A thrown value that is not an `Error`** (a string, `undefined`, an object with no `message`). It classifies as `Unexpected` with safe text, and the person sees `UNEXPLAINED`. (Task 1)
4. **A very long error message.** The text sent to Sentry is cut to 300 characters; the text shown to the person is not cut. (Task 3)
5. **Hostnames.** `ok-tuner-lightning-jar.vercel.app` is production; `ok-tuner-git-feat-x-lightning-jar.vercel.app` and a hashed deployment hostname are preview; an empty hostname is development. (Task 2)
