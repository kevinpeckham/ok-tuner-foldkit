# OK Tuner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port the Stem Shovel guitar tuner into this Foldkit app, idiomatically, and get it ready to deploy on Vercel.

**Architecture:** The microphone and its analyser are a Foldkit managed resource that exists only while the Model says the tuner is on. A subscription reads it every 50 ms and sends one Message per reading; `update` owns the needle smoothing and the hold-then-clear logic; the view derives the note, cents and nearest string. Pitch detection, tunings and saved preferences are pure modules.

**Tech Stack:** Foldkit 0.170.0, Effect 4.1.0, `@foldkit/ui` 0.170.0, Tailwind 4, Vite 8, vitest 5 (happy-dom), oxfmt, oxlint, Bun 1.4.5.

**Spec:** `docs/superpowers/specs/2026-11-24-tuner-design.md`. Read it first; this plan argues from it.

## Review Focus

Conditions the spec implies but does not spell out, most likely first. Each is pinned by a test in the task named.

1. **A reading arrives after the tuner is turned off** (a tick already in flight): it is ignored and the tuner stays off. Task 3.
2. **The microphone is refused, then the person presses the button again:** the error shows, and the second press tries again from a clean state. Task 3.
3. **Opening the microphone fails half-way** (the stream opened, the audio context did not): the stream's tracks are stopped, so no microphone stays open. Task 4.
4. **Saved preferences are damaged** (not JSON, wrong types, A4 out of range, an unknown tuning): the tuner starts on defaults for the damaged part and does not crash. Task 2.
5. **Junk in the A4 field** (empty, letters, 399, 481): nothing is applied or saved, a later valid value still applies, and closing the menu puts the applied value back in the field. Task 6.

```ts
export const WINDOW = 4096
export type MicrophoneHandle = Readonly<{
  stream: MediaStream
  context: AudioContext
  analyser: AnalyserNode
}>
export const Microphone = ManagedResource.tag<MicrophoneHandle>()('Microphone')
export type MicrophoneService = ManagedResource.ServiceOf<typeof Microphone>
export const REFUSED =
  'Microphone access was refused. Allow it in the browser to tune.'
export const UNSUPPORTED = 'This browser cannot open the microphone.'
export const acquireMicrophone: Effect.Effect<MicrophoneHandle, unknown>
export const releaseMicrophone: (
  handle: MicrophoneHandle,
) => Effect.Effect<void>
export const microphoneErrorReason: (error: unknown) => string
export const readMeasurement: (
  handle: MicrophoneHandle,
  buffer: Float32Array,
) => Measurement
```

- Produces, from `src/main.ts`: `export const managedResources` with one entry, `microphone`; `export const subscriptions` with one entry, `readings`. `update` now returns `Update.Return<Model, Message, MicrophoneService>`.

**Decisions:**

- `acquireMicrophone`: fail with an error whose reason maps to `UNSUPPORTED` when `navigator.mediaDevices?.getUserMedia` is missing. Otherwise request `{ audio: { echoCancellation: false, noiseSuppression: false, autoGainControl: false, sampleRate: { ideal: 48000 }, channelCount: { ideal: 1 } } }`, create an `AudioContext`, `resume()` it when its state is not `'running'` (ignore a failed resume), create an analyser with `fftSize = WINDOW` and `smoothingTimeConstant = 0`, and connect the stream source to it. **If anything after `getUserMedia` fails, stop the stream's tracks before failing.**
- `releaseMicrophone`: stop every track, close the context; never fails.
- `microphoneErrorReason`: `REFUSED` when the error's `name` is `'NotAllowedError'`; `UNSUPPORTED` for the missing-API failure; otherwise the error's own `message`, or `'The microphone could not be opened.'` when it has none.
- `readMeasurement`: `analyser.getFloatTimeDomainData(buffer)`, then `measure(buffer, context.sampleRate)`.
- `managedResources.microphone`: required (`Option.some`) while `model.tuner` is `Starting` or `Listening`; `onAcquired → Message.SucceededAcquireMicrophone()`, `onReleased → Message.ReleasedMicrophone()`, `onAcquireError → Message.FailedAcquireMicrophone({ reason: microphoneErrorReason(error) })`.
- `subscriptions.readings`: depends on `{ isListening: boolean }`. While listening, `Stream.tick('50 millis')`; **on every tick** it gets `Microphone` and emits `Message.MeasuredInput(...)`, and emits nothing on a tick where the resource is not available (`ResourceNotAvailable`). It allocates one `Float32Array(WINDOW)` per stream, not per tick. The per-tick lookup matters: in dev, Vite restores the Model after a reload without running `init`, so the page can boot already `Listening` before the microphone is reacquired.
- `entry.ts` passes `managedResources` and `subscriptions` to `Runtime.makeApplication`.
